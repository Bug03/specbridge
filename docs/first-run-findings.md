# First-run findings

Observed during the first local PR-review setup. Keep this list current as the first-run flow improves. Do not put private repository findings or credentials in this public document.

## Environment issues

| Issue | What happened | Workaround used | Product follow-up |
| --- | --- | --- | --- |
| GitHub account mismatch | The browser account differed from the active `gh` identity, so a private repository was unavailable to the CLI. | Authenticated the intended account with `gh auth login --web`; verified the active login with `gh api user --jq .login`. | Add a short preflight that shows the active GitHub login and checks repository access before creating a review session. |
| SSH clone failed | `gh` selected SSH, but the active account did not have an SSH key configured. `gh auth setup-git` retained/reset the SSH protocol. | Set `gh config set -h github.com git_protocol https` after Git credential setup. | Prefer HTTPS for initial setup or report the selected Git protocol and a clear remediation when clone fails. |
| Diff context exceeded limit | A large multi-file PR exceeded SpecBridge's 600,000-character cap when the diff included 50 lines of context. | Reduced context to 10 lines; the checkout remains available for the reviewer to inspect surrounding code. | Add file-based diff batching for large PRs and report partial coverage clearly if a PR still exceeds the limit. |
| Codex model mismatch | The local Codex CLI defaulted to `gpt-6-luna`, which this ChatGPT-backed CLI account rejected. | Set the review default to `gpt-5.6-terra`, with `SPECBRIDGE_CODEX_MODEL` as an override. | Add a reviewer preflight that checks the selected model before cloning and explains how to choose a supported model. |
| Usage exhausted during rerun | A full rerun to regenerate a report hit the Codex account usage limit. | Kept the first completed result; did not issue more Codex calls. | Persist each review stage and finding as it completes; support resume without paying to repeat successful stages; show token/time usage and remaining work in the UI. |
| One-pass review has limited depth | The first SpecBridge run completed one Codex pass. It did not run dedicated discovery, independent validation, or synthesis passes. | Treat the report as an initial pass and verify cited locations against the captured PR head. | Build a staged, resumable pipeline with explicit per-stage progress, per-finding evidence and validation, and an honest coverage summary before producing a final review. |
| Temporary checkout paths leaked into report links | The first report linked to files under a temporary directory that SpecBridge deletes after completion. | Added conversion to stable GitHub links in the report generator; the successful report still needs regeneration after usage becomes available. | Keep all report evidence anchored to the PR head SHA and never expose ephemeral workspace paths. |
| Run output has no review workspace | The CLI prints a final block of findings but offers no stage timeline, per-finding validation state, review controls, or final-comment composer. | Saved the report locally and labeled it partial. | Add a run dashboard with progress, inspectable finding notes, and a copy-only final comment composer. |
| Ollama Docker image is expensive to pull on ARM64 | The image exposed a 2.5 GB ARM64 layer and the pull made no visible progress during the smoke test. | Switched to the much smaller TEI CPU ARM64 image for a local embedding runtime check. | Compare native Ollama, Ollama Docker, and TEI setup cost before selecting the one-click default; report image/model sizes before downloading. |
| Qwen3 embedding did not start in the TEI CPU ARM64 image | TEI downloaded the Qwen3 config/tokenizer, then failed because the model repository had no `onnx/model.onnx` file for that CPU backend. | Stopped the failed container and tried a TEI-compatible ONNX code embedding model. | Test exact model/runtime/architecture combinations in CI or a smoke matrix; do not infer a model is supported just because another TEI backend supports it. |
| TEI default warmup exceeded container memory | The Jina code embedding ONNX model was downloaded, but TEI was OOM-killed during warmup with its default batch/tokenizer settings. | Restarted it with `--max-batch-tokens 2048`, `--max-batch-requests 2`, `--max-client-batch-size 4`, `--max-concurrent-requests 8`, and `--tokenization-workers 2`; it then served requests at about 1.75 GiB RSS. | Set conservative, architecture-aware defaults and show Docker memory limits before model startup; increase throughput settings only when resources allow. |
| Embedding request exceeded configured batch limit | A synthetic request with nine inputs returned HTTP 422 after the test server was capped at four inputs per client batch. | Split the smoke test into requests with three inputs each; all succeeded. | Make the ChunkHound adapter honor the configured max client batch size and retry in smaller batches on this validation error. |
| Local code embedding smoke test is promising but small | Three synthetic code-search cases ranked the relevant snippet above a distractor, but this does not establish quality on real repositories or Vietnamese ticket text. | Recorded vector size (768 dimensions), request success, and timing as a smoke test only. | Evaluate on a sanitized fixture set with real call-site and requirement retrieval before naming a default. |
| Jira issue context returned HTTP 404 | The configured Jira connection did not return the linked issue, so ticket acceptance criteria were not available to the review pipeline. | Continued with the PR description, checked-in OpenSpec, tests, and source; did not claim Jira context was included. | Add a preflight that distinguishes wrong site/project/key and access denial, then show which context sources were actually loaded. |
| ChunkHound silently completed with zero embeddings when TEI rejected large batches | ChunkHound 5.2.1 indexed 34 files and 469 chunks, sent batches of 15–60 items to TEI configured for a maximum of 4, logged HTTP 422 errors, then exited successfully while reporting 0 embeddings. | Reconfigured TEI's max client batch and ChunkHound to use `batch_size: 4` with `max_concurrent_batches: 1`; a rerun generated all 469 embeddings. | Treat an index as incomplete when embedding errors occur or indexed chunks have no vectors; preflight and align ChunkHound batch/concurrency with the selected embedding server. |
| ChunkHound's default embedding concurrency overloaded the local TEI service | Raising TEI's maximum client batch size alone exposed ChunkHound's default of 8 concurrent embedding batches; TEI rejected requests with HTTP 429 `Model is overloaded`. | Capped ChunkHound to one concurrent embedding batch and a batch size of four. Indexing 469 chunks then took about 125 seconds on this Apple Silicon Docker CPU setup. | Use conservative hardware-aware defaults, make concurrency and batch progress visible, and tune them with a measured preflight instead of assuming API-provider concurrency is safe for local CPU inference. |
| ChunkHound did not recognize the Jina model name in tiktoken | ChunkHound logged a warning that tiktoken could not map `jinaai/jina-embeddings-v2-base-code` and fell back to a character-count heuristic. | Indexing and semantic retrieval still completed with the local TEI endpoint. | Verify the token-aware batch sizing and truncation behavior for custom model identifiers; surface the fallback in setup diagnostics. |
| ChunkHound cold index timed out on a large source file | A scoped first index completed most files but skipped one large file after its parser timeout while reporting zero file errors. | Reindexed the affected file with `--force-reindex`, `--no-cleanup`, and a longer per-file timeout; a subsequent full index completed. | Report timed-out files as incomplete coverage; retry large files with a longer timeout and reuse the existing index. Make cold-index progress and retry actionable in the UI. |
| Independent Codex validation stalled on an internal cache error | A second read-only Codex pass stopped making progress after logging `missing field base_instructions` while renewing its cache TTL; no validation result was produced. | Stopped that pass and manually checked the candidates against the pinned diff, OpenSpec acceptance criteria, and existing tests. | Make review stages resumable and expose tool failures as stage status; retry a failed validation pass without repeating completed discovery or indexing. |
| A shell health-check script used a reserved zsh variable name | The first health-check loop assigned to `status`, which zsh treats as read-only, so that check stopped before evaluating the service. | Renamed the variable to `http_code` and continued the health check. | Keep setup scripts compatible with the user's default shell and smoke-test the shell fragments used by the guided setup. |

## Review quality notes

- The desired full review setup includes GitHub access, a user-selected Codex or Claude CLI reviewer, a local ChunkHound index, and a reranker served from a local Docker container. Embeddings can be generated locally or through OpenRouter `baai/bge-m3`; disclose that the hosted option sends indexed source text outside the machine. SpecBridge should show setup/indexing time separately from analysis time and must not label a run complete if either required retrieval service did not run.
- Reports should connect user journeys and business outcomes to separate technical analysis. Include strengths, supported in-scope findings, explicit out-of-scope or unknown areas, assumptions, downgrade factors, code evidence, reproduction paths, and revision provenance where applicable.
- Review depth depends on a strong review contract, enough analysis budget, useful retrieval, independent finding validation, and an honest coverage summary. Measure setup components rather than assuming indexing alone makes a review deeper.
